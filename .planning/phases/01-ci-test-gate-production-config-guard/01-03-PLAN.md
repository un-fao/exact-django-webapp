## Phase Goal (MVP)

**As a** maintainer of the live EX-ACT backend, **I want to** have a deploy blocked whenever the test suite fails, a high-severity security finding appears, or production config is unsafe, **so that** a broken or insecure build never reaches App Engine.

This plan is the integration slice: it wires the code and prerequisites from waves 1 into an actual pipeline gate. After it lands, a maintainer can open a PR and watch the suite run against real Postgres, and a failing test or scan visibly blocks deploy. It runs in wave 2 because it consumes files created by plans 01-01 (api/checks.py) and 01-02 (settings.py TEST.NAME, test_seed_data.json, requirements-dev.txt); the shared `deploy.yaml` file is owned exclusively by this plan.

## Artifacts this phase produces (plan 01-03)

- New `test` job in `.github/workflows/deploy.yaml` (job id `test`) with a `postgres:15` service container
- New `pull_request` trigger (branches develop, main, review) on the workflow `on:` block
- New `needs: test` dependency and `if: github.event_name == 'push'` guard on the `deploy` job
- New `APP_MODE` env var on the `Deploy` step (branch ternary, reused from the job-level `environment:` expression)
- New `python manage.py check --deploy` step in the `deploy` job (between `migrate` and `collectstatic`)
- New `bandit --severity-level high` and `pip-audit -r requirements.txt` steps in the `test` job

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted PR branch -> CI runner | A pull_request from any contributor triggers the test job; it must not have deploy privileges or leak secrets |
| CI workflow -> production App Engine | Only a passing test job on a push event may reach `gcloud app deploy`; unsafe config must be rejected first |
| GitHub secrets/generated credentials -> job logs | Injected secrets and the generated Firebase credential must never be echoed into logs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | `deploy` job starting despite a failing suite or scan | high | mitigate | `needs: test` edge plus `if: github.event_name == 'push'`; a red test job blocks deploy and PRs never deploy (D-01) |
| T-03-02 | Elevation of Privilege / config bypass | SEC-03 check silently never firing because `APP_MODE` is unset in the deploy job | high | mitigate | Add `APP_MODE` via the branch ternary to the Deploy step env, then run `manage.py check --deploy` on real values (Finding 9, D-13) |
| T-03-03 | Information Disclosure | New steps echoing app.yaml/settings.py or the generated Firebase credential into logs | high | mitigate | Preserve the do-NOT-echo NOTE comments; the credential step writes only base64 to `$GITHUB_ENV` and is never printed; no new echo of substituted files |
| T-03-04 | Tampering (red-herring green) | Bare test label silently skipping most unit tests or crashing on api/tests/old | high | mitigate | Explicit enumerated dotted-path label list (Finding 8); first-CI-run test count is the human verification per Pitfall 1 |
| T-03-SC | Tampering | Supply chain via `pip install -r requirements-dev.txt` in CI | high | mitigate | Pins verified and human-approved in plan 01-02 (T-02-SC); this job installs only those pinned versions |
</threat_model>
