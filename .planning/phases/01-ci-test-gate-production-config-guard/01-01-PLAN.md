<objective>
Deliver SEC-03: a Django deploy-time system check in a new `djangoexact/api/checks.py` that fails `manage.py check --deploy` when `APP_MODE` is `production` and either `DEBUG` is True or `CORS_ALLOWED_ORIGINS` is empty, registered through `ApiConfig.ready()`, and covered by a database-free unit test that simulates the unsafe and safe env combinations.

## Phase Goal (MVP)

**As a** maintainer of the live EX-ACT backend, **I want to** have a deploy blocked whenever the test suite fails, a high-severity security finding appears, or production config is unsafe, **so that** a broken or insecure build never reaches App Engine.

Note: the ROADMAP `**Goal:**` line for Phase 1 is outcome-shaped (a CI/infra hardening phase on a brownfield app, WALKING_SKELETON disabled), so the strict UI vertical-slice pattern does not apply. The story above is a faithful restatement of that goal, not new scope. This plan delivers one complete, independently testable slice of it: the production config guard end to end (check code + registration + passing unit test).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI/deploy pipeline -> production runtime config | The env values (APP_MODE, DEBUG, CORS_ALLOWED_ORIGINS) chosen at deploy time cross into the running production app; an unsafe combination must be rejected before `gcloud app deploy` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `settings.py` DEBUG + `CORS_ORIGIN_ALLOW_ALL = DEBUG` reaching production | high | mitigate | `check_production_config` emits Error `api.E001` when APP_MODE=production and DEBUG is True, failing `manage.py check --deploy` (D-11/D-12) |
| T-01-02 | Information Disclosure | Empty `CORS_ALLOWED_ORIGINS` in production | high | mitigate | Error `api.E002` fails the deploy check when CORS list is empty under production |
| T-01-03 | Tampering (of the guard itself) | Check registered at `Warning` level, or keyed on `settings.APP_MODE` which is always None | high | mitigate | Use `Error` (not `Warning`) per D-11 and read `os.getenv("APP_MODE")` per Finding 5; unit test asserts Error ids fire under production and stay silent otherwise |
</threat_model>
