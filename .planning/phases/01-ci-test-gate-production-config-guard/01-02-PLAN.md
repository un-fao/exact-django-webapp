<objective>
Deliver the repository-side prerequisites the CI test job (plan 01-03) consumes: (1) a `TEST.NAME` override on the non-GAE `DATABASES["default"]` branch in `settings.py` so `manage.py test --keepdb` reuses the database that `migrate` + `load_reference_data` already populated instead of building an empty `test_<DB_NAME>` (Finding 2); (2) a small `api/fixtures/test_seed_data.json` `loaddata` fixture containing the two `Group` rows and two `CustomUser` rows that the existing test base classes look up but that no manifest, migration, or signal creates (Finding 2b); and (3) a new `djangoexact/requirements-dev.txt` pinning bandit and pip-audit for CI/local parity (D-08).

These are the shared foundation the workflow depends on; they must exist in the repo before plan 01-03 can call them.
Output: one-line settings.py edit, `api/fixtures/test_seed_data.json` (new), `requirements-dev.txt` (new), gated by a package-legitimacy human checkpoint.

## Phase Goal (MVP)

**As a** maintainer of the live EX-ACT backend, **I want to** have a deploy blocked whenever the test suite fails, a high-severity security finding appears, or production config is unsafe, **so that** a broken or insecure build never reaches App Engine.

This plan is the shared-foundation slice of that goal: it makes the test database genuinely reachable by reference data and seed rows (so a "green" run is real, not a red herring per PITFALLS.md Pitfall 1) and pins the two security scanners. It is grouped horizontally by necessity: plan 01-03's single `deploy.yaml` test job consumes all three artifacts, and MVP mode permits a shared-foundation grouping when a later slice depends on it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PyPI package registry -> CI runner and developer environments | New dev dependencies (bandit, pip-audit) are fetched and executed in CI; a wrong-name or malicious package would run with pipeline privileges |
| Repo fixtures -> test database | test_seed_data.json rows are loaded into the CI database; a bad fixture could mask or fake test outcomes |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-SC | Tampering | `pip install` of `bandit`/`pip-audit` from `requirements-dev.txt` | high | mitigate | Pin exact researched versions (bandit==1.9.4, pip-audit==2.10.1); blocking-human legitimacy checkpoint verifies PyCQA/PyPA ownership on pypi.org before the pins are trusted (never auto-approvable) |
| T-02-01 | Tampering (correctness / red-herring green) | Suite running against an empty `test_<DB_NAME>` with no reference data | high | mitigate | TEST.NAME override enables `--keepdb` reuse of the migrated+seeded DB; test_reference_bootstrap.py (run in plan 01-03) proves fixtures actually loaded |
| T-02-02 | Spoofing / Information Disclosure | Seed CustomUser password hashes in a committed fixture | low | accept | Throwaway test-only accounts on ephemeral CI databases; no real credential value, and tests authenticate via force_authenticate (Finding 7), so the hash grants no meaningful access |
</threat_model>
