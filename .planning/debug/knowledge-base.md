## excel-inventory-missing-mods: Excel report Inventory sheet omitted all seven non-land module families
- **Date:** 2026-07-31
- **Error patterns:** no inventory data available for this project, inventory sheet empty, missing inventory rows, irrigation inputs energy packaging transport storage processing not picked up, silent omission no error, empty Inventory(), activity data in tCO2-eq column
- **Root cause(s):** `BaseCalculator.inventory` discovered its math module through a hardcoded five-name attribute whitelist (`math_start`, `math_start_w`, `math_start_wo`, `math_w`, `math_wo`) and returned an empty `Inventory()` on a miss, so the seven container families contributed zero rows; their container calculators built per-entry sub-calculators as throwaway locals and kept no math module of their own, and Transport/Storage/Packaging entry calculators store theirs under `energy_math_*` / `electricity_math_*`; `OperationPhaseIrrigation` passed `InventoryPerGasPerActivity(0, GasTypes.X, activity)` into a `(gas_type, value, activity)` signature, which would raise TypeError the moment the inventory was actually aggregated; module caches persisted the empty inventory and were validated only against `last_modified`, so existing projects would keep serving empty rows after the code fix; separately, `Inputs` and `NewIrrigation` wrote activity data (`unit_start` tonnes, `units_start` hectares) into a column headed "Value (tCO2-eq)" because `input_single_calculation` computed `emissions_start` and then discarded it
- **Fix:** replaced the whitelist with `MATH_COMPONENT_GROUPS` (one representative per component, summed across components); added `_track_entry_calculator` / `_reset_entry_calculators` / `entry_calculators` to BaseCalculator and wired all seven containers so entry inventories roll up; corrected the three swapped `InventoryPerGasPerActivity` calls; added `INVENTORY_SCHEMA_VERSION` with invalidation scoped to the eight affected module types so the fix self-heals existing projects; made `input_single_calculation` return `emissions_start` and recorded it in the three `Inputs` rows, with 0 for `NewIrrigation` to match the `Roads` precedent
- **Files changed:** djangoexact/api/calculators.py, djangoexact/api/reports/cache.py, djangoexact/math_model/no_time_dependency_final/inputs.py, djangoexact/math_model/no_time_dependency_final/general_functions.py, djangoexact/api/tests/test_inventory_rollup.py
- **Why not caught:** no gate existed for this class. The failure was a silent empty-list fallback rather than an exception, and the Inventory sheet's "No inventory data available" placeholder is indistinguishable from a legitimately empty project. No test asserted that a given module family contributes inventory rows, and `pytest` does not run in CI (tests are a local pre-PR gate only), so nothing would have flagged it even if such a test had existed. The value-semantics half was doubly hidden: those rows could never reach a report while the roll-up defect suppressed them.
- **Recurrence guard:** regression test `djangoexact/api/tests/test_inventory_rollup.py` (26 tests), notably `MathComponentGroupTests::test_every_group_name_is_a_real_attribute_somewhere`, which greps the calculators source and fails if any name in `MATH_COMPONENT_GROUPS` stops being assigned anywhere, catching the exact drift the old whitelist suffered; plus `InputsInventoryValueTests::test_no_row_reports_the_raw_input_quantity`, which fails if an inventory row ever again carries the raw input quantity. Structural guard: `INVENTORY_SCHEMA_VERSION` in the cached payload, so any future fix that changes a module's inventory can invalidate stale caches instead of being masked by them.

### Reusable lessons

- A lookup that returns an empty collection on a miss is a silent failure. Prefer raising, or at minimum log, when a discovery mechanism finds nothing. The empty `Inventory()` fallback is what turned a plumbing gap into an invisible one for the whole life of the codebase.
- When a report reads a value off object A while the real work happens on throwaway object B, the numbers can be right on one sheet and absent on another. If the Results sheet is correct but a summary sheet is empty, suspect two different objects rather than a rendering bug.
- Verifying a cache-backed fix contaminates the evidence. The first fixed-code render writes corrected rows, after which a reverted build reads them back and appears to pass. Pick a subject whose cache the session has not touched, or the before/after proves nothing.
- Before trusting a "this is how it has always been" value, check whether the producing function even returns the right quantity. Here the correct value was computed and thrown away one stack frame below the call site.

## import-project-loses-results: exported projects arrived uncomputed, and exporting destroyed the source project's results
- **Date:** 2026-08-11
- **Error patterns:** imported project has no results, modules read as not computed after import, have to recompute every module after importing, my results disappeared, results gone after downloading a project, export does not carry cached results, module status resets to EMPTY on import, silent no error
- **Root cause(s):** four independent defects composing. (D, dominant) `Project.save()` bulk-invalidates every module cache whenever a dirty field falls outside its `exclude_fields` allowlist, and `export_id` was absent from that list, so the export action's `project.save(update_fields=['export_id'])` wiped the caches of the project being exported *before* the serializer ran, meaning the file never contained results at all; (A) `ModuleExportSerializer.excluded_fields` listed `status`, so imported modules were forced to EMPTY and the results endpoint refused them at `views.py:2613` before ever consulting the cache; (B) the same tuple listed `last_modified`, the timestamp `is_cached_results_valid()` compares `last_cached_at` against, so any restored cache read as stale; (C) `CachedResultMixin.save()` calls `parent.invalidate_cached_results()` on every submodule save and the importer creates submodules after the parent, wiping a cache written at create time
- **Fix:** added `export_id` to `Project.save`'s `exclude_fields`; dropped `status` and `last_modified` from `ModuleExportSerializer.excluded_fields`; in `import_project`, popped the cache and status columns out of the payload before `objects.create()` and replayed them once the whole module tree exists via `Model.objects.filter(pk=...).update(...)`, which bypasses `save()` and so cannot re-invalidate or re-stamp. Restore is keyed on field presence so older files import unchanged, and exported `StatusType` PKs are validated first so a file from an installation with different reference data degrades to EMPTY instead of aborting on an FK violation
- **Files changed:** djangoexact/api/models.py, djangoexact/api/serializers.py, djangoexact/api/views.py, djangoexact/api/tests/test_project_export.py
- **Why not caught:** no gate existed for this class. `test_project_export.py` already covered the round trip but asserted only on inputs, never on computed state, so an export that carried no results at all looked correct. The dominant cause was invisible from reading either endpoint in isolation: the invalidation happens in `Project.save()`, three files away from both the exporter and the importer, and is triggered by a field write (`export_id`) that has nothing to do with the science. `pytest` does not run in CI (local pre-PR gate only), so even a good test would not have blocked it.
- **Recurrence guard:** regression tests in `djangoexact/api/tests/test_project_export.py` (8 tests), notably the one asserting the **source** project still holds valid cached results after `GET /export/`, which is the only guard on cause D and the only one whose symptom is invisible at import time; plus tests pinning `status` and `last_modified` into the payload, a parent cache surviving submodule creation, byte-identical `cached_results_*` round trip with `is_cached_results_valid()` True, and an older-build payload importing unchanged. Ablation-verified: reverting any single fix with the other three in place fails at least one test.
- **Historical impact (open, product-side):** every export performed before this fix silently destroyed that project's cached results in production. The fix prevents recurrence but restores nothing. Affected users report it as "my results disappeared" or "I have to recompute". Recomputation is the recovery path; inputs were never touched. No remediation code or blast-radius query was written by design. See the Historical data loss section in the resolved session file.

### Reusable lessons

- A save-time invalidation hook keyed on an allowlist is a trap: every new field added to the model defaults to "invalidates the cache", including bookkeeping fields that have nothing to do with the cached computation. `export_id` was a file identifier, not science, and it silently joined the invalidation set just by existing. Prefer an explicit deny-list of fields that *do* invalidate, or assert the allowlist's completeness in a test.
- When a round trip loses data, check whether the *producer* still has the data at the moment it serializes. The instinct is to debug the importer, and here three of four causes were on the import side, but the dominant one had already destroyed the data before serialization began. The exported file is the cheapest place to look: if the field is absent from the JSON, the importer is not the suspect.
- `objects.create()` followed by child creation is unsafe whenever the child's `save()` reaches back and mutates the parent. Writing derived state during create and expecting it to survive is the bug; replay it with `queryset.update()` after the tree is complete, which deliberately bypasses `save()`.
- "I think I already fixed this" is a hypothesis, not evidence. All four candidate branches carried the byte-identical broken code, and the branch most likely to hold the fix was zero commits ahead of develop. Diffing the branches took minutes and eliminated the theory outright, which was worth doing first precisely because it would have been the cheapest possible fix.
- A cache that is *cleared* rather than *marked invalid* destroys the forensic trail. Nothing in the data distinguishes "damaged by this bug" from "never computed", which is what makes the historical blast radius unsizeable from the cache columns alone.
