## Approach

Before changing any pin, establish which of the 7 alerts are genuinely
unpatched on `develop`. Dependabot evaluates alerts against the repository's
default branch (`main`), and `main` trails `develop`, so an open alert is not
by itself evidence that `develop` is vulnerable.

### Task 1: Resolve each alert to its patched version and compare against develop

- Pull the authoritative patched version and vulnerable range for every open
  alert from the Dependabot API rather than inferring from advisory titles:
  `gh api repos/un-fao/exact-django-webapp/dependabot/alerts?state=open`
- Read the installed version of each package on `develop`:
  - pip: `djangoexact/requirements.txt`
  - npm: `djangoexact/package-lock.json` (all `node_modules/<pkg>` keys,
    including nested duplicates)
- Compare `origin/main` versions for the same packages to confirm or reject
  the stale-alert hypothesis.
- **Verify:** every alert classified as either PATCHED-ON-DEVELOP or
  ACTIONABLE, with the installed version recorded next to the patched version.
- **Done:** classification table complete for all 7 alerts.

### Task 2: Bump only the genuinely unpatched pins

- For each ACTIONABLE alert, raise the pin to at least
  `first_patched_version` in `requirements.txt` / `package-lock.json`.
- Skip any alert classified PATCHED-ON-DEVELOP. Re-pinning a package that is
  already above the patched version is a no-op that adds churn and risks
  regressions for no security gain.
- **Verify:** `py_compile` gate plus a re-read of the manifests.
- **Done:** no ACTIONABLE alert remains without a corresponding bump.
