# Quick Task 260805-n82: Summary

## Outcome

**All 7 open alerts are already patched on `develop`. No dependency pin needed
to change.** The alerts remain open because Dependabot evaluates the repository
against its default branch `main`, and `main` is 14 commits behind `develop`
and still carries the vulnerable versions. They will close on their own the
moment `develop` reaches `main`.

## Files changed

None. No production or test code was touched, and no pin was raised.

Raising a pin here would have been churn with no security benefit: every
installed version already exceeds `first_patched_version`.

## What actually closes these alerts

Promoting `develop` to `main` through the normal release path. PR #264
(`develop` -> `review`) is the first leg of that. The alerts are a property of
`main`'s dependency snapshot, not of the code under review, so nothing in this
repository's working tree can clear them.

## Notes

This reproduces the pattern recorded on 2026-07-15: the standing majority of
open high and medium Dependabot alerts on this repository are stale relative to
`develop` because scanning is pinned to the lagging default branch. On that
earlier sweep exactly one alert (PyJWT) was genuinely unpatched. On this sweep,
zero are.

The informational bot comment on PR #264 reports repository-level alert state,
which is computed against `main`, so it will keep listing these 7 on every
`develop` PR until the merge lands. That is expected behaviour, not a
regression in the PR under review.
