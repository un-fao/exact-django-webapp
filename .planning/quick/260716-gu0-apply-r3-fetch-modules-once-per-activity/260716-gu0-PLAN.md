<objective>
Apply R3 from the 260716-g2x report-performance research: fetch each activity's module list once per report request and reuse it through the report path, plus select_related on the per-type module queries, eliminating the Activity.modules re-query storm (research hotspot H2).

Purpose: `Activity.modules` is a property that re-runs 1 + N_types queries on every access. Per Excel report request it runs twice per activity (readiness pre-pass at models.py:776 and BaseActivityReport.compute at base.py:200) plus one StatusType lazy-load per module in the pre-pass. Per PDF template request, html_context.py reads it ~12 times per activity through the is_luc/is_fishery/is_livestock/is_energy/is_storage/is_transport/is_processing/is_packaging/is_input/area properties and its own module loop.

Output: Per-instance opt-in memoization on Activity plus select_related("status"), with the api report view sharing one materialized activity list across both passes. No schema changes, no migrations, no fixture edits, no public API changes.

**Chosen mechanism (planner judgment, from the delegated decision):** an opt-in per-instance memo consulted by the existing `modules` property, primed by a new idempotent `cache_modules()` method. This was picked over explicit list-passing (would require signature changes in is_ready, generate_excel_report, BaseProjectReport, and BaseActivityReport) and over a report-scoped cache object (same plumbing cost). The memo is scoped to the Python instance lifetime, so code that never calls `cache_modules()` is untouched, satisfying "do not change behavior of non-report code paths".

**Cross-pass sharing (considered as requested, adopted):** Project.is_ready is called from exactly one place in the codebase (api/views.py:713, verified by grep; public/views.py:150 calls it with no args, which is a different flow). The api report view can therefore share one fetch per activity across the pre-pass and compute by materializing the queryset once and having generate_excel_report filter is_b_intact in Python instead of cloning the queryset. This is behavior-identical because is_b_intact is `BooleanField(default=False)` (models.py:1013), non-nullable, so `not a.is_b_intact` matches the ORM filter exactly. The public report view keeps its current structure (is_ready runs before activities are parsed there; reordering it is out of scope) and still benefits from select_related and the compute/html_context priming.

**select_related scope (deviation from the research's suggested list, per its own "verify which FKs the downstream code actually touches" instruction):** only `status` is added. Modules are fetched through the activity's reverse related managers, so Django's known-related-objects mechanism already populates `module.activity` with the same parent instance at zero queries; adding select_related("activity", "activity__project") would replace that shared instance with fresh per-row copies, breaking memo reuse and widening every per-type query. `status` is the one per-module FK the report path lazy-loads (Module.is_ready at models.py:1442-1443).
</objective>

Three edits inside the Activity class plus one in Project.is_ready, all in djangoexact/api/models.py. Reference the R3 decision from the locked task context in the commit body if useful; no D-NN ids exist for quick tasks.

1. Rewrite the `modules` property (currently at ~1031-1033) to consult a per-instance memo before delegating:
   - Read `getattr(self, "_modules_memo", None)`; if it is not None, return it; otherwise return `self.__get_all_modules()` as today.
   - The memo attribute is a plain Python attribute, not a model field. No migration is needed or allowed.

2. Add a new public method `cache_modules(self)` next to the property. It must be idempotent: if `getattr(self, "_modules_memo", None)` is None, set `self._modules_memo` to the result of the private all-modules fetch, then return `self._modules_memo`. Note an empty activity memoizes `[]`, which is not None, so it will not re-fetch; this is intended. Docstring must state: read-only report paths call this once per Activity instance so later `modules` reads and the derived properties (is_luc, is_fishery, area, and friends) reuse one fetched list; never call it around code that adds or removes modules; the memo lives only for this Python instance's lifetime and is never persisted. Name-mangling note: the method lives inside the Activity class, so calling the double-underscore private fetch method via self resolves correctly.

3. In `__get_all_modules` (~1183-1190), append `.select_related("status")` to the per-type queryset built from `getattr(self, module_type.class_name.lower()).all()`. Every concrete module class inherits the `status` FK from the abstract Module base (models.py:1424), so this is uniform and safe. Do NOT add "activity" or "activity__project": reverse-manager fetches already share the parent Activity instance via Django's known-related-objects, and joining activity would replace it with fresh per-row instances, defeating the memo (rationale in plan objective).

4. In `Project.is_ready` (~771-779), change the inner loop to iterate `activity.cache_modules()` instead of the plain property, so the pre-pass primes the memo on each activity instance it receives. Verified: the only call site passing activities is api/views.py:713; public/views.py:150 calls it with no args and is unaffected in behavior (fresh instances, one fetch each, status now joined).

Do not touch module_type_for_class, get_ready_status, or anything else from the R1/R2 commits. No em-dashes anywhere.
