<objective>
Extend `reconcile_stale_async_jobs` with a second, deferred sweep that removes the orphaned
empty shell Projects left behind when an async project copy fails.

Purpose: the async copy path creates the destination Project up front (`views.py:1294`,
`create_project_shell`) and returns its id to the client immediately. When the worker job
fails, that shell stays in the user's project list forever as an empty ghost entry. Cleanup
must be deferred, not immediate, so the polling client still sees the failure attached to a
real project before the link disappears.

Output: an extended management command, a test class covering it, and an updated guide.
</objective>

  <name>Task 1: Add the deferred orphan-shell sweep to reconcile_stale_async_jobs</name>
  <files>djangoexact/api/management/commands/reconcile_stale_async_jobs.py</files>

  <behavior>
    Given a PROJECT_COPY AsyncJob, the sweep deletes its linked Project only when ALL hold:
    - status is FAILED
    - completed_at is not null and is older than the 24 hour grace period
    - the linked Project has zero activities
    - params["target_project_id"] equals job.project_id
    - params["source_project_id"] does not equal job.project_id
    In every other case the job and its Project are left completely untouched.
    After a successful delete the AsyncJob row still exists, still FAILED, with its
    error_message and params intact and project_id NULL.
  </behavior>

  <action>
    VERIFY FIRST (D-04): before writing any delete, confirm `Project.delete()` has plain
    Django semantics. Run `grep -n "class Project(" djangoexact/api/models.py` and
    `grep -n "class Historical(" -A 5 djangoexact/api/models.py`. Expected: Project inherits
    only `Historical` and `DirtyFieldsMixin`, and `Historical` declares nothing but a
    `HistoricalRecords` manager. Also confirm no `delete` override exists on the Project
    class body. If either expectation fails (a soft-delete or archive mixin is present, or
    delete is overridden), STOP and report the finding instead of proceeding, because the
    whole approach depends on delete() being a real row delete.

    Then extend the command file:

    Add a module-level constant `ORPHAN_SHELL_GRACE = timedelta(hours=24)` next to the
    existing `STALE_THRESHOLD`, with a short comment explaining the grace exists so a
    polling client can read the failed status and error_message before the project link is
    removed (D-01). Import `transaction` from `django.db`.

    Leave the existing stale-flip block exactly as it is (D-06). Extract nothing from it,
    rename nothing in it. In `handle()`, after the existing
    `self.stdout.write(f"Reconciled {count} stale AsyncJob(s).")`, call a new private method
    that performs the sweep and writes its own summary line, for example
    `Deleted {n} orphaned shell project(s) from failed copies.`

    The sweep method selects candidates with a single queryset filtering on
    `kind=AsyncJob.Kind.PROJECT_COPY`, `status=AsyncJob.Status.FAILED`,
    `completed_at__lt=cutoff` and `project__isnull=False`, using `select_related("project")`.
    Note in a comment that a FAILED row with a null completed_at is deliberately skipped:
    without that timestamp there is no anchor for the grace window, and every current
    failure path stamps it.

    For each candidate apply the guards in this order, skipping the job on any failure:
    1. Read `params = job.params or {}`. Skip unless
       `params.get("target_project_id") == job.project_id`.
    2. Skip if `params.get("source_project_id") == job.project_id`. This pair of checks is
       the hard guarantee that the sweep can only ever touch a copy destination, never a
       user's source project (D-02).
    3. Skip if the linked project has any activities. Use an `exists()` query, not a count.

    Then perform the removal inside a single `with transaction.atomic():` block (D-03):
    re-run the activities `exists()` check inside the block and skip if it now returns True,
    so a project that gained an activity between selection and deletion survives; set
    `job.project = None` and `job.save(update_fields=["project"])`; then call
    `project.delete()`. The unlink must be the first statement because AsyncJob.project
    cascades, so deleting first would take the failed job row with it, and the atomic block
    means a failing delete rolls the unlink back rather than orphaning the job.

    Count successful deletions and return the count. Do not swallow exceptions into a bare
    `except: pass`: if you guard the per-job body at all, catch `Exception`, log it with the
    job pk via the module logger, and continue to the next job so one bad row cannot abort
    the whole sweep.

    Keep the command's `help` text accurate by appending a sentence about the new sweep.
    No em-dashes anywhere in the file.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator/scheduler to database | The command runs unattended (Cloud Scheduler is the recommended trigger) and performs irreversible row deletion of user-owned data with no human in the loop. |
| AsyncJob.params to delete target | `params` is JSON written by the API at enqueue time but is untrusted at read time: a hand-edited or legacy row could name any project id. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-h79-01 | Tampering | sweep delete target | critical | mitigate | Delete only when `params["target_project_id"] == job.project_id` AND `params["source_project_id"] != job.project_id`, so a mislinked or hand-edited row can never route the delete at a user's source project (Task 1 guards 1 and 2). |
| T-h79-02 | Denial of service | user's in-use project | high | mitigate | Zero-activities check, re-run inside the atomic block immediately before delete, so a project the user has started populating is never removed (Task 1 guard 3, Task 2 test 2). |
| T-h79-03 | Repudiation | failed AsyncJob audit row | medium | mitigate | `AsyncJob.project` is CASCADE, so the job is unlinked and saved before `project.delete()`, both inside one `transaction.atomic` block; the failure record and its error_message survive for support and debugging (Task 2 test 1). |
| T-h79-04 | Denial of service | polling client | medium | mitigate | 24 hour grace on `completed_at` guarantees the client has read the failure before the project link is cleared (Task 2 tests 3 and 7). |
| T-h79-05 | Information disclosure | n/a | low | accept | The change adds no endpoint and no new data exposure; the command is operator-run and writes only aggregate counts to stdout. |

No package-manager installs are introduced by this task, so no supply-chain legitimacy
checkpoint applies.
