# Quick Task 260727-h79: Deferred orphan-shell sweep for reconcile_stale_async_jobs Summary

**Extended `reconcile_stale_async_jobs` with a second, deferred pass that hard-deletes the empty shell Project of a failed PROJECT_COPY AsyncJob after a 24-hour grace period, guarded by an activities-emptiness check and a params-based source/target guard, unlinking the job inside one atomic block before deleting the project.**

## Performance

- **Duration:** 20 min (approximate)
- **Completed:** 2026-07-27
- **Tasks:** 3 completed
- **Files modified:** 3

## Accomplishments

- `reconcile_stale_async_jobs` now runs a second pass after its existing stale RUNNING/PENDING flip: it finds FAILED PROJECT_COPY jobs whose `completed_at` is older than a new `ORPHAN_SHELL_GRACE` (24 hours), verifies the linked project is genuinely the copy's empty destination (not a source), and hard-deletes it while preserving the AsyncJob row with its status, error_message and params intact and `project` set to NULL.
- Seven new tests cover: successful delete plus job preservation, a shell with an activity surviving, the grace window, wrong kind, wrong status, the source-project guard, and the interaction with the pre-existing flip in a single command run.
- `docs/guides/async-jobs.md` "Reconciliation of stale jobs" section now documents both passes, the grace period rationale, the three safety conditions, and the null-`completed_at` limitation, plus a note that the existing hourly Cloud Scheduler recommendation already covers the new sweep.

## Decisions Made

- Confirmed via `grep` on `api/models.py` that `Project(Historical, DirtyFieldsMixin)` has no delete override and `Historical` declares only a `HistoricalRecords` manager, so `Project.delete()` is a plain hard delete (D-04). This was the plan's mandatory VERIFY FIRST step; no soft-delete or archive mixin was found, so the delete-based approach proceeded as planned.
- Followed the plan's exact guard ordering: target-id match, then source-id mismatch, then an `exists()` (not `count()`) activities check, then a re-check of that same `exists()` inside the `transaction.atomic()` block immediately before the unlink-then-delete.
- Used a broad `except Exception` per job (logging via the module logger with the job pk) rather than letting one malformed row abort the whole sweep, per the plan's explicit instruction against a bare `except: pass`.
