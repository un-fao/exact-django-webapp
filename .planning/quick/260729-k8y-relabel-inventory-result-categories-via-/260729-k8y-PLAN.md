<objective>
Rename the IPCC Category labels shown in Inventory results, in the online per-module
results API and in the offline Excel report Inventory sheet, without touching the math
layer.

Purpose: the current labels come straight from the ActivityTypes enum, which doubles as
an identity key for emission-set filtering and for the persisted per-module caches. The
enum therefore cannot be renamed. A presentation-layer mapping applied at display time
gives the wanted wording while leaving every stored value and every filter untouched.

Output: a new api/inventory_labels.py mapping module, a database-free unit test for it,
and three call sites wired to it (the results API action, the live report path, the
cached report path).
</objective>

    - inventory_label(fake_aquaculture, "N2O Field") returns "FISH EMISSION (EXCRETA)" (module override wins)
    - inventory_label(fake_aquaculture, "Electricity") returns "Electricity emissions (CO2-eq)" (module override wins)
    - inventory_label(fake_input_module, "N2O Field") returns "N2O Field" and inventory_label(fake_input_module, "Electricity") returns "Electricity" (override is Aquaculture-only, other modules unchanged)
    - inventory_label(fake_aquaculture, "Biomass") returns "Biomass Carbon stock" (an overridden module still gets the defaults for other categories)
    - idempotency invariant: the set of every produced label, defaults plus all override values, is disjoint from the set of mapping keys, so applying the mapping twice equals applying it once
    - idempotency in practice: for every key k, inventory_label(module, inventory_label(module, k)) equals inventory_label(module, k), checked for both a plain module and an Aquaculture module

  <action>
Create `djangoexact/api/inventory_labels.py`. It imports nothing: no Django, no models, no
math_model. Give it a short module docstring explaining that it is a presentation-layer
mapping applied when Inventory rows are rendered, that the ActivityTypes enum in
math_model stays the identity key for filtering and for persisted caches, and that it is
therefore never edited.

Define exactly three module-level names.

`DEFAULT_LABELS`, a dict of raw ActivityTypes value to new label, containing precisely
these eleven pairs and nothing else: "Soil CO2 Change" to "Soil Carbon stocks (SOC)";
"Soil Organic Matter" to "Soil Organic mineralization"; "Biomass" to "Biomass Carbon
stock"; "AGB Growth" to "AGB STOCK"; "BGB Growth" to "BGB STOCK"; "Litter" to "LITTER
STOCK"; "Deadwood" to "DEAD WOOD STOCK"; "Catch" to "FISHERIES EMISSIONS (FUEL)";
"Refrigerant" to "Refrigerant emissions (CO2-eq)"; "Ice" to "Ice emissions (CO2-eq)";
"Coastal Waterbodies" to "Waterbody emissions (CH4)".

`MODULE_OVERRIDES`, a dict of module class name to a per-module override dict, containing
exactly one entry: key "Aquaculture", value a dict mapping "N2O Field" to "FISH EMISSION
(EXCRETA)" and "Electricity" to "Electricity emissions (CO2-eq)". Add a comment on that
entry recording the reason: those two ActivityTypes members are shared with the
Inputs and Electricity math modules, whose wording must not change, so the rename is
scoped to Aquaculture only.

`inventory_label(module, category)`, which resolves overrides first, then defaults, then
falls back to the category itself:
look up `MODULE_OVERRIDES.get(type(module).__name__, {})`, and return the override entry
for `category` if present, otherwise `DEFAULT_LABELS.get(category, category)`. Key the
override strictly on the Python class name. Do not read `module.module_type.name`: that
field is registered with modeltranslation and its value changes with the active request
language.

Create `djangoexact/api/tests/test_inventory_labels.py` covering the `<behavior>` list.

`api.inventory_labels`, and stand in for modules with tiny local classes whose names match
the real model classes, for example `class Aquaculture: pass` and `class Input: pass`
declared inside the test module. Do not import or instantiate any Django model.

Write the disjointness check as a real assertion over the data structures: collect every
value from `DEFAULT_LABELS` plus every value of every override dict in `MODULE_OVERRIDES`,
collect every key from `DEFAULT_LABELS` plus every key of every override dict, and assert
the intersection is empty. This is what guarantees a second pass of the mapping is a no-op,
which matters because relabeled strings can reach a rendering path more than once.

Wire all three call sites. Add the import `from api.inventory_labels import inventory_label`
to each of the three files, matching the absolute-import style already used for sibling
api modules (`from api.defaults import DefaultsFactory` in views.py, `import api.models as
api_models` in reports/base.py).

Site A, the online API. In `djangoexact/api/views.py`, inside `GenericModuleViewSet.results`,
insert the relabel after `module.cache_results(...)` and immediately before
`serializer = DynamicResultSerializer(module_results, aggregate_by=aggregate_by)`. That one
position covers both branches: the cached branch where `module_results` came from
`module.get_cached_results(by=aggregate_by)` and holds the old strings persisted by earlier
runs, and the fresh-compute branch. Placing it after `cache_results` also keeps the
persisted cache raw, which is required since the stored strings are identity keys.

Build new objects rather than editing in place. On the cached branch `module_results` is
the in-memory value of a model JSON field, so mutating it would put presentation labels on
a live `module.cached_results_*` attribute that a later save could persist. Read
`module_results.get("inventory")` only when `module_results` is a dict; when that value is
a list, build a fresh list where each element that is a dict carrying an "activity" key is
replaced by a shallow copy with "activity" set to `inventory_label(module, entry["activity"])`,
and every other element is carried over untouched; then rebind `module_results` to a shallow
copy of itself with the new list under "inventory". Handle the other shapes by doing nothing:
the TOTAL breakdown stores a plain number there, the GAS breakdown a list of dicts with no
"activity" key, and older caches may have no "inventory" key at all. Leave the non-inventory
results keys alone; the frontend aggregates those independently of the wording and they are
out of scope here.

Site B, the live Excel report path. In `djangoexact/api/reports/base.py`, in
`_inventory_items_from_module`, pass the label through the mapper when building each
`InventoryItem`: the `ipcc_category` argument becomes `inventory_label(self.module,
item.activity.value)` for the branch where `item.activity` is set, and keeps the existing
"N/A" string for the branch where it is not. Do not send "N/A" through the mapper.

Site C, the cached Excel report path. In `djangoexact/api/reports/cache.py`, in
`build_inventory_from_cache`, the local `activity` variable holds the raw stored string and
already defaults to "N/A" when the entry has none. Keep that default resolution as is and
pass the result through the mapper for the `ipcc_category` argument only, as
`inventory_label(module, activity)`. Leave `activity_name`, `module_name`, `gas_type` and
`value` untouched.

Do not modify `api/reports/renderer.py`: it receives `InventoryItem` objects that are
already labeled. Do not modify anything under `djangoexact/math_model/`.
